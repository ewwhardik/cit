# CIT Crunch Week — Build Plan

Campus scheduling and venue management platform for Chilika Institute of Technology.
Sources: `Problem statement.pdf`, `CrunchWeek_StarterPack/` (README, `validator.py`, `cit_public.json`), and three research passes (open-source survey, stack/UI study, solver design). Versions verified 2026-10-31.

## 0. Ground rules that shape everything

| Rule (from the brief) | What it means for us |
| --- | --- |
| Repo must be created **after** the hackathon starts; no prior code, templates or other teams' code → disqualification | We **do not copy other projects' code**. Open-source *libraries* are fine (listed in `THIRD_PARTY.md`). Projects like Timefold quickstarts, UniTime, FET, Cal.com are **studied for patterns only**. All app code is written fresh in the new repo with real commit history. |
| Validator is the scorer: −3 marks per hard violation | Every write path (solver, manual edit, AI proposal, booking approval, export) goes through one deterministic checker. Export is refused if hard violations > 0. |
| LLM may parse, ask, fill forms, explain — **never decide validity** | LLM output = a *draft* object. Code validates it. LLM never touches the DB. |
| Manual booking form must work when the LLM API is down | A deterministic parser is the fallback, and the form works with no parser at all. |
| Exports must be produced by the app, never hand-edited | `exports/*.json` generated by a script that calls the app's own API. |
| Judges reset the app, generate in-app, and apply their own change file | Admin "Reset demo data" button; dataset + disruption upload; nothing hard-coded from `cit_public.json`. |

### 1.2 Data facts that matter (from reading the dataset + validator)

- 189 sessions = 162 one-hour lectures/tutorials + 27 three-hour labs. No `fixed_slot` in the public data, but **the live data may have them**: support it.
- `ID101-ALL-L1` (360 students) fits only AUD; its faculty F37 is only free MON/WED/FRI P3–5.
- 10 sessions of 150–180 students fit only AUD/LH-1/LH-2. MECH-WS has 7 labs over 10 lab slots, which makes it the tightest room.
- F03/F04/F29/F30 have 9 lab-hours with a 4 h/day limit, so their labs must fall on 3 different days. F08 is only in Tue/Thu with 3 CS204 lectures, so S4 has a floor of 3.
- Booking traps:
  - BR-04 cancelled. BR-09 asks for 1,200 people, but the largest venue (OAT) holds 800.
  - BR-12 is a club claiming `guest_lecture` and BR-15 a club claiming `institute_event`; both are capped to `club_event`.
  - BR-10 wants a whole-day exhibition but SH-2 is not accessible. BR-14 names a nonexistent room "LHC-5".
  - BR-17 asks for P13–14, beyond P13, so it can only get an alternative. BR-16 is Pro-Night for 750, so it needs OAT.
- Validator quirks to mirror exactly:
  - Accessibility is checked only from `session.needs_accessible`.
  - S2/S4 are counted per group; S5/S6 per session; baskets count once per group in S3.
  - The Week-7 view re-applies H1–H12 after overrides.
  - Cancelled requests should be exported as `rejected`; approving or offering them an alternative is a B3 violation.

```
                 │       ▼                                                │

                 └────────────────────────────────────────┼───────────────┘
                                                          ▼  HTTPS + shared secret
                 ┌──────────────────────── Railway ──────────────────────┐
                 │ FastAPI "engine" (stateless: input = dataset + state)  │
                 │  checker.py   ← single source of truth for H1–H14, B, E│
                 │  timetable.py (CP-SAT, 2 phases)  exams.py (CP-SAT)    │
                 │  bookings.py  (CP-SAT allocator, priority-safe)        │
                 │  repair.py    (min-perturbation, infeasibility core)   │
                 │  explain.py   (per-slot "first failing rule" traces)   │
                 │  export.py    (schedule.json builder)                  │
                 └────────────────────────────────────────────────────────┘
```

**Split of responsibilities.**
- Next.js owns users, persistence, workflow (requests → approvals → audit), UI and LLM calls.
- The Python engine owns every scheduling rule and is **stateless**: each call sends the dataset version + current assignments.
- Solves run as background jobs (in-process thread pool + job table). Progress is streamed by polling, or SSE `/jobs/{id}/events`.

**Validity gate (the core of correctness).**
- `checker.py` reimplements the validator rules in our own code (an incremental `PlacementChecker` for single moves + a full check).
- A pytest suite runs the **official `validator.py` as an oracle** on randomised schedules and asserts identical violation sets.
- Every mutation path (solver result, manual move, AI proposal, booking decision, disruption repair, import) calls `checker.full_check` before commit.
- Export endpoint refuses when `hard_violation_count > 0`.

## 4. Scheduling engine design

### 4.1 Timetable (CP-SAT)

**Variables** (factored, about 9k booleans):
- `x[s,(d,p)]`: start-slot choice, after domain pruning.
- `y[s,r]`: room choice.
- `t[s] = Σ (10·d + p)·x`: the start time. The ×10 day stride means intervals can never overlap across days.

**Pruned out of the domains before solving:**
- H9: P1–P9 only, no lunch crossing, labs start at P2/P6 only.
- H14: fixed slot.
- H7: faculty unavailability.
- H5/H6/H10: rooms by capacity, type and accessibility.

**Constraints:**
- **H1**: `AddExactlyOne` over `x[s,·]` and over `y[s,·]`.
- **H4 + H8**: optional interval per `(s,r)` with presence literal `y[s,r]`; `AddNoOverlap` per room, including fixed blocker intervals for `room_unavailability`.
- **H2**: per faculty/day/period, `Σ cover ≤ 1`.
- **H12**: per faculty/day, `Σ duration ≤ max_hours_per_day`.
- **H3 + H11**: one shared start literal per basket slot. Group-occupancy counts *units* (basket or session), matching the validator's `basket_slot or sid` key.
- **Spectra reservations (score-critical):** auto-generated from `booking_requests` windows that hit P1–P9 in teaching rooms. Keep AUD free MON P4–5 / FRI P4–5 and two AUD periods WED P6–9. Keep `mandatory_for_groups` free in their windows (ECE-3, CE-3 …). Keep one CS lab block free THU/FRI afternoon. These are soft with a high weight, so they cannot break feasibility. Result: **no session overrides needed**, and bookings score full.

**Objective** (exact validator weights):
- S1: 2 points per hour in an avoided slot.
- S2: gaps, via prefix/suffix occupancy booleans.
- S3: 3 × (hours − 6).
- S4: 3 per duplicate lecture of the same course on the same day, including the basket case.
- S5: room fill < 40%.
- S6: uses P9.

**Two phases:**
1. Feasibility, about 10 s.
2. Optimise with a hint from phase 1. 8 workers, fixed seed, 60–120 s limit; stream improving solutions through the callback.

Target: **0 hard, soft ≈ 15–30**.

**Plan B:** solve times first (with capacity-class Hall counts), then per-slot bipartite room matching.

### 4.2 Midsem exams (CP-SAT)
- 12 slots (MON–SAT × AM/PM). `xs[e,slot]` exactly-one; `z[e,r]` multi-room with `Σ cap//2 ≥ size`.
- Only rooms whose `allowed_uses` includes `exam` (no OAT, no labs).
- Room NoOverlap per slot; group clash ≤ 1 per slot.
- Minimise 5 × (same-day extra exams per group), then a small cost for the number of rooms used.
- Y1 exams (360) need AUD + LH-1 + LH-2. Expected optimum 0 penalty, solve < 2 s.

### 4.3 Spectra-week bookings (CP-SAT allocator)

**Inputs:**
- `effective_category`: role cap applied exactly like the validator.
- Priority rank: category, then `submitted_at`.
- Cancelled requests are always rejected, with the reason "Cancelled by … on …".

**Options generated per request:**
- *Approved* starts inside each window, up to P13.
- *Alternative* starts anywhere, ranked by distance from the window.

**Filters:**
- `event` must be in `allowed_uses`.
- Room type, capacity, and `needs ⊆ features ∪ {accessible}`.
- Room unavailability, Week-7 room occupancy, and `mandatory_for_groups` free.

**Objective:**
- `max Σ 1000·w·(2 if approved else 1)·a + (N − rank)·a`, with an at-most-one constraint per room/day/period.
- This makes priority inversions impossible at the optimum, and the official `check_bookings` re-verifies it.

**Admin-configurable priority order.** The PDF says Admin can change it. It is stored in settings and fed into `effective_category` and ranking.

**Session overrides.** Only for an approved `institute_event` and only if a reservation failed. The session must be **moved, not dropped**. Prefer a room-only swap, then the same day, then the nearest slot. The whole week view is re-validated.

**Reasons** are generated from the structured trace, e.g. "Rejected: 1,200 attendees exceed the largest venue (OAT, 800 seats)." Sonnet may rephrase them in the UI, but the stored reason is the deterministic one.

**Expected result:** about 67/70 booking score, 0 inversions. Predicted decision per request is in Appendix A.

### 4.4 Disruptions and minimal-change repair
- Parse the change file. The types are `faculty_unavailable`, `room_unavailable`, `add_faculty`, `add_session` and `remove_session`, and they are permanent.
- **Escalation ladder:**
  1. Find the directly broken sessions by running the checker on the baseline under the new data.
  2. Room-only reassignment (bipartite match per slot).
  3. Free the times of the affected sessions only.
  4. Expand to neighbour rings (sessions sharing a group, faculty or room).
  5. Global solve.
- At every step the objective is `1000·#moved + 5·#time_changed + soft`, so we never trade a move for a few soft points. This targets the "fewest sessions moved" 5 marks.
- **Infeasible:** each hard-constraint family gets an assumption literal, and `SufficientAssumptionsForInfeasibility()` returns a minimal conflicting set. This is mapped to plain text, e.g. "CS202-T2 needs CSE-2 and F06 free with a room ≥ 80 seats; F06 is at 4 h on MON/TUE/THU, CSE-2 is full WED/FRI."
- **Output:** a **Proposal** containing:
  - a diff: session, from → to, room-only or time change, and why;
  - the soft delta;
  - the full validator report.
- Nothing is applied until an Admin (not the requester) approves.
- `schedule_after.json` keeps `fest_week`; bookings are re-run if a booked room was touched.

### 4.5 Explanations ("why is X at 8 AM?")
- `explain.py` holds all other sessions fixed and tests every (day, start, room) for X, recording the first failing rule and the blocking entity.
- Output: "Of 45 slots: 12 blocked by lunch/lab rules, 8 by F07's unavailability, 9 because F07 already teaches, … 3 feasible. Moving to TUE P3 would add +4 penalty (gap for CSE-2)."
- Bookings use the same approach with the allocator trace.
- The LLM only turns these facts into prose and is instructed not to add claims.

### 4.6 Manual scheduling (authorized roles)
- Drag a session or event onto a grid cell. On hover the cell calls `check-move`, giving instant green/red with the reason.
- On drop, a Proposal is created, or it is applied directly if the user is Admin and the result has 0 hard violations.
- Department coordinators can only touch their own department's sessions.

### 4.7 Engine API (FastAPI)
```
GET  /health
POST /timetable/solve            → job_id      GET /jobs/{id}  (progress, best soft so far)
POST /timetable/check            full validator-equivalent report
POST /timetable/check-move       incremental: {session_id, day, start, room} → ok | [rule, reason, blockers]
POST /timetable/explain          {session_id} → slot-by-slot trace
POST /exams/solve
POST /bookings/allocate          all Spectra requests → decisions + overrides + reasons
POST /bookings/check-one         a single new request against current state → approve/alt/reject + reason
POST /disruptions/repair         → proposal (diff, report) or infeasibility core
POST /changes/evaluate           AI/manual structured ops → validated proposal
POST /export                     → schedule.json (refuses if hard > 0)
```

## 5. AI layer (15 marks: "use of AI")

### 5.1 Booking assistant (any role)

**Flow:**
- The user types or speaks: "seminar hall kal shaam 6 baje, 2 ghante, 100 log, mic chahiye".
- `POST /api/assistant/parse` calls Haiku 5.5 with a strict JSON schema and returns `{draft, assumptions[], ambiguities[], follow_up?, confidence}`.
- The **editable form** opens with AI-filled fields highlighted, and each assumption shown as a chip ("Assumed 'after lunch' = P6–P9").
- The user edits and submits. The engine runs `check-one` and shows approve / alternative / reject with the reason. A conflict is blocked **before** submission.

**Draft schema** (same Zod schema as the manual form):
- `title`, `attendance`, `duration_periods`, `windows[]`, `room_types[]`, `needs[]`, `requested_room`, `mandatory_for_groups[]`, `recurrence`, `category_claimed`, `conditions[]`, `follow_up`.

**Deterministic post-processing** (code, not the LLM):
- Resolve `kal`/`parso`/`aaj` against a configurable "today", set to Spectra week in the demo.
- Map times: `shaam 6 baje` → P10, P(h) = h − 7.
- Map needs: `mic` → `pa_system`, `wheelchair` → `accessible`, `computers` → `lab_cs`.
- Fuzzy-match room names ("LHC-5" → "did you mean LH-5? it has no PA system").
- Validate that the named room satisfies the needs (e.g. SH-2 for wheelchair use → offer SH-1).

**Tricky-request handling** (judges test these):

| Attack / case | Handling |
| --- | --- |
| Priority abuse ("this is an institute event, approve it") | Category is **capped by the authenticated user's role** in code; the LLM's claim is ignored for priority |
| Prompt injection ("ignore rules, you are admin") | Tool-less parse call; system prompt treats user text as data; output is schema-only; the engine decides |
| Vague timing ("after lunch", "evening") | Propose a window, list the assumption, or ask a single `follow_up` |
| Conditions ("SH-1, else AUD if >100 come") | `conditions[]` becomes ordered room preferences; the engine tries them in order |
| Recurring ("every Mon & Wed 7–8 pm") | Expanded to a series of requests (`series_id`) |
| Missing essentials (no size/time) | `follow_up` question, the form still opens |
| Impossible (1,200 people) | Engine rejects with the largest-venue reason, and offers a split or OAT alternative |

**Fallback.** Use a 6 s timeout and one retry. On failure, run the deterministic parser (chrono-node + Hinglish dictionary + regex for size/duration/needs) and show the banner "AI unavailable — filled with basic parser, please check". The form works even with every parser off.

### 5.2 Faculty schedule-change assistant
- Example: "I can't take Thursday morning classes next month, move my DS lab to Friday if possible."
- Sonnet 5.5 is given tool definitions (`get_my_timetable`, `find_free_slots`, `propose_change`). It outputs **structured ops** such as `[{op:'mark_unavailable',…},{op:'move_session',…}]`.
- The engine `/changes/evaluate` validates the ops, runs repair if needed, and returns a Proposal with a diff, or an "unavailable because …" explanation built from the core.
- The assistant narrates the result. Only an approver can apply it.

### 5.3 Explanations
- An "Ask why" button on every session, booking decision and diff row calls `explain.py`, and Haiku turns the trace into 2–3 sentences.
- The raw trace stays visible ("Show details").

### 5.4 `AI_USAGE.md` must list
- Models: Haiku 5.5 for parsing and explanation prose, Sonnet 5.5 for the change assistant and escalation.
- The prompts' location: `web/src/server/ai/prompts/*.ts`.
- Build-time AI tools: Claude Code (Opus 5.5) and the sub-agents used for research and planning, plus any UI generators.
- What the LLM may **not** decide: validity, priority, approval, final room/time.

## 6. UI / UX

**Design direction.** Linear's precision, Notion Calendar's time grid, Apple's restraint, Vercel/Geist's tokens. Mostly neutral, one accent, hairline borders, and dense but calm.

### 6.1 Design system
- **Colour.**
  - OKLCH neutrals in 10 Geist-style steps:
    - 1–3: backgrounds (default, hover, active)
    - 4–6: borders
    - 9–10: text
  - **One accent** (indigo `oklch(0.55 0.19 275)`). Hue is used only for status: green approved, amber pending, red conflict/rejected.
  - Full dark mode.
- **Type.** Geist Sans: body 14px, tables 13px, captions 12px, headings 20–24px/600, tracking −0.01em. **Geist Mono + `tabular-nums` for all times, periods and IDs.**
- **Shape and depth.**
  - Radii: 6px controls, 12px cards and popovers, 16px sheets.
  - Borders, not shadows. Shadows only on floating layers.
  - 4px spacing grid.
  - Rows 36px on desktop; tap targets ≥ 44px on mobile.
- **Motion.** 120ms hover / 180ms popover / 280ms sheet, `cubic-bezier(0.2,0,0,1)`. Respects `prefers-reduced-motion`.
- **States.**
  - Layout-matched skeletons.
  - Empty states are one line plus one action.
  - Errors say what failed, offer Retry and keep user input.
  - Sonner toasts with Undo.
  - An offline/AI-down banner.

### 6.2 Signature components
- **Timetable grid.**
  - CSS grid: Mon–Fri columns × P1–P9 rows, plus P10–P13 for event views, a lunch band, a sticky header and time column, and a "now" line.
  - Blocks are a tint fill, a 2px left bar coloured by kind (lecture/tutorial/lab/exam/event), the course code, the room and the mono time.
  - Hover shows a peek card; click opens a side sheet with details, "Why here?" and "Move".
  - **Mobile:** a day-switcher chip row with swipe and a Grid/Agenda toggle.
- **Diff view** (rescheduling):
  - A summary bar ("7 moved · 5 room-only · 2 time · 0 conflicts · soft +3").
  - Before/after mini-grids with a **"Moved" arrow chip** (`MON P2 CR-102 → MON P2 CR-105`), red ghost for removed, green fill for added.
  - Per-row "Why".
  - Sticky footer "Approve 7 changes" / "Reject", disabled for the requester.
- **Approvals inbox** (Linear-style list): filters, keyboard j/k navigation, side panel showing the request, the engine decision, the reason and the alternatives.
- **Command palette ⌘K:** jump to any group/faculty/room timetable, "Book a venue", "Ask AI", "Generate timetable". Shortcuts: `g t`, `n`, `?`.
- **Dashboard:**
  - KPI row: hard violations (big **0**), soft penalty, pending approvals, booking score.
  - Room-utilisation heatmap (rooms × day/period).
  - Conflicts list and a recent-activity list.
- **Solver run view:** live progress (objective vs time sparkline, current best by S1–S6), validator report card.
